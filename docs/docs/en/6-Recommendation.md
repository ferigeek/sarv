# Recommendation Service

This document describes the Recommendation Service — an independent Python (FastAPI) service responsible for content ranking and personalized feed generation.

It covers purpose, quickstart, configuration, API contract, candidate generation, scoring, pagination, integration with the Core Backend, and deployment. It reflects the **current state of the implementation**.

---

## Overview

The Recommendation Service does not manage users or store application data. It reads candidate posts directly from the shared PostgreSQL database, ranks them, and returns a paginated list of `post_id` + `score` to the Core Backend. The backend hydrates full `Post` entities via `findAllByIdsFiltered` preserving rank order and builds `Page<PostResponse>` (see [5-Backend.md](./5-Backend.md)).

Key properties:

- Stateless — can be horizontally scaled (multiple instances behind a load balancer)
- Synchronous — ranking is on the critical path of `GET /api/feed/recommended` but degrades gracefully to chronological on failure
- Shared database — reads `posts` and `follows` tables (no writes)

## API Reference

### `GET /health`

Health probe for `docker-compose.yaml` (`interval 10s, timeout 3s, retries 3, start_period 10s` — `python -c "urllib.request.urlopen('http://localhost:8000/health')"`).

- **Auth:** none (internal network)
- **Response `200`:**
```json
{ "status": "ok", "model": "heuristic-v1" }
```

### `GET /feed`

Returns ranked post IDs with scores, paginated server-side. Called by `RecommendationClient.java:26` as `GET /feed?user_id=&page=&size=`.

**Query Parameters:**

| Param | Type | Required | Validation | Description |
|-------|------|----------|------------|-------------|
| `user_id` | string | yes | — | `users.id` as string (`Long` from Spring `userRepository.findByUsername → getId`) |
| `page` | int | no | `ge=0` | Zero-based page index (default `0`) |
| `size` | int | no | `ge=1, le=100` | Page size (default `20`) |

Validation errors return `422 Unprocessable Entity` (FastAPI automatic).

**Response `200`:**

```json
{
  "user_id": "42",
  "posts": [
    { "post_id": "123", "score": 12.3 },
    { "post_id": "87", "score": 8.1 }
  ],
  "page": 0,
  "size": 20,
  "total": 87
}
```

- `posts` ordered `score desc`; pagination is `paged = ranked[page*size : page*size+size]`; out-of-range `page` returns `[]` not error.
- `total` = pre-pagination count (used by backend as `Page` `totalElements` in `FeedService.java:65`).
- Sorting is always `score desc` — any client `sort` on `GET /api/feed/recommended` is ignored (sanitized to unsorted `PageRequest` in `FeedController.java:42`).

**Example:**

```bash
curl "http://localhost:8000/feed?user_id=42&page=1&size=10"
```

> **Note on contract:** the service currently returns both `post_id` and `score`. The intended contract is `post IDs only`; the backend currently ignores `score` except for order and hydrates via `findAllByIdsFiltered`. See [3-Architecture.md](./3-Architecture.md#recommendation-system).

**Errors:**
`422` for invalid `page/size`, `500` for DB failures (no custom handler — FastAPI default).

## Candidate Generation

`CandidateGenerator(user_id).generate_candidates()` (`candidate.py`) combines three sources (`search_span_days=7`) via one async `_fetch` helper and deduplicates preferring the flagged copy (`trending → following → follower` order).

All queries filter `deleted_at IS NULL AND type='NORMAL' AND created_at >= now - 7d` (UTC):

**1. Trending (`_get_trending_posts`, limit 100):**
```sql
SELECT id, like_count, dislike_count, view_count, created_at
FROM posts
WHERE deleted_at IS NULL AND created_at >= %s AND type='NORMAL'
ORDER BY (like_count + view_count) DESC, created_at DESC
LIMIT 100
```
Note: ordered by `like_count + view_count` (ignores `dislike_count`; scoring penalizes it).

**2. Following (`_get_following_posts`, limit 50):**
```sql
SELECT p.id, p.like_count, p.dislike_count, p.view_count, p.created_at
FROM posts p JOIN follows f ON p.user_id = f.followed_id
WHERE f.follower_id = %s AND p.deleted_at IS NULL AND p.created_at >= %s AND p.type='NORMAL'
ORDER BY p.created_at DESC LIMIT 50
```
`from_followed=True` on `PostFeatures`.

**3. Follower (`_get_follower_posts`, limit 50):**
```sql
SELECT p.id, p.like_count, p.dislike_count, p.view_count, p.created_at
FROM posts p JOIN follows f ON p.user_id = f.follower_id
WHERE f.followed_id = %s AND ...
ORDER BY p.created_at DESC LIMIT 50
```
Also `from_followed=False` (no boost for mere followers).

Max raw candidates: `100 + 50 + 50 = 200` before dedup. Connections come from a shared `AsyncConnectionPool` opened in the app `lifespan` (`database.py` `open_pool`/`close_pool`, `DB_POOL_MIN/MAX/TIMEOUT`). Per-source latency and counts are observed as `feed_db_query_seconds{query}` / `feed_candidates_count{source}`.

Backed by `V9__add_recommendation_indexes.sql`: partial `idx_posts_trending` for the engagement sort and partial `idx_posts_user_type_created_at` for the follow timelines.

## Scoring

`PostFeatures` dataclass (`scoring.py`):

```python
post_id: str
like_count: int
dislike_count: int
view_count: int
created_at: datetime
from_followed: bool = False
author_id: str = ""
comment_count: int = 0
author_affinity: float = 0.0
user_boost: float = 1.0
```

`score_post(features, now=None)` (`heuristic-v1`):

```python
engagement = 2 * like_count + view_count + 3 * comment_count - 2 * dislike_count
engagement = max(engagement, 0)

age_hours = max((now - created_at).total_seconds() / 3600, 0)
recency_boost = 1 / (1 + age_hours / 48)  # half-life ~48h

follow_boost = 1.5 if from_followed else 1.0
affinity_boost = 1 + min(max(author_affinity, 0), 10) * 0.1  # 1.0-2.0

return engagement * recency_boost * follow_boost * affinity_boost * user_boost
```

- Engagement weighted `2×` likes/dislikes, `3×` comments, `1×` views, clamped to 0.
- Recency decay `1/(1+t/48h)` → 50% at 2 days, 33% at 4 days.
- Follow boost `1.5×`; affinity boost `1.0` (cold) to `2.0` (capped at 10 points).
- `user_boost` in `0.9-1.1` from the user's like/comment rate (`engagement_boost`), `1.0` with no views.

*Example:* 10 likes, 100 views, 2 comments, 1 dislike, 12h old, from followed, affinity 5 → `(20+100+6-2)*0.8*1.5*1.5 ≈ 223.2`.

## Behavior signals

Two extra queries per `/feed` (same connection, ridden indexes, timed as `affinity`/`engagement`):

- **Author affinity** (`_get_author_affinity`, 30d window): `event_logs JOIN posts` grouped by author with weights `VIEW=1, LIKE=3, COMMENT=4, REPOST/QUOTE=5, DISLIKE=-2` (plain views; dwell deferred). Cold authors score `0`.
- **User engagement** (`_get_user_boost`, 30d window): one aggregate of `VIEW/LIKE/COMMENT` counts → `engagement_boost` rate multiplier.
- A `V10 (user_id, type, created_at)` index is deferred — `EXPLAIN` first on staging-size data.

The `ranked = sorted(candidates, key=score_post, reverse=True)` determines final order.

## Learned ranker (lr-v1)

`LogisticRegression(class_weight=balanced)` over the shared 8-dim vector (`scoring.to_vector`: log counts, raw age, follow flag, capped affinity, user boost), `StandardScaler` pipeline, seeded shuffle split.

- **Labels:** LIKE/COMMENT/REPOST/QUOTE positive, DISLIKE negative, 1:4 random un-touched negatives (feed impressions are not logged, so shown-but-ignored is unsamplable; dwell excluded for P3).
- **Caveats:** features are current counters, not as-of-impression snapshots (documented leakage); event logging is best-effort. Heuristic-vs-learned engagement comparison lands in the Intelligent-Feed PDF (P5).
- **Runbook:** `uv run python train.py --build-only --out data/train.csv` then `uv run python train.py --train --in data/train.csv` → `models/model.pkl` + `metadata.json` (metrics: accuracy, log-loss, AUC, P@10 vs prevalence). Artifacts are gitignored — retrain locally.
- **Serving** (`model.py`): loads `MODEL_PATH` at startup, ranks by `P(positive)`; missing/corrupt artifact or per-request error falls back to heuristic. `/health` and `feed_model_info` report the active ranker (`lr-v1` vs `heuristic-v1`); the versioned cache key retires stale pages.

## Caching

Read-through Redis (`cache.py`): key `feed:{MODEL_VERSION}:user:{id}:page:{p}:size:{s}`, value `{posts, total}`, TTL `FEED_CACHE_TTL_SECONDS` (45s). The key derives from `MODEL_VERSION`, so formula bumps retire stale pages automatically. Hits skip the DB; any failure logs `WARN` and bypasses. Observed as `feed_cache_events_total{outcome}`.

## Pagination & Contract

- `page` zero-based, `size` 1–100, validated by FastAPI `Query`.
- `total` is pre-pagination count; backend uses it as `Page.totalElements` (`FeedService.java:65`) and preserves rank order even after filtering invalid `post_id` strings or missing/deleted rows (may cause last-page holes).
- Out-of-range page returns `posts: []` with same `total`.
- Intended contract is IDs-only; current `score` is for debugging and ignored by backend except for sort.

## Integration with Core Backend

`GET /api/feed/recommended` (`FeedController.java:37`) flow:

1. Resolve `userId` from `UserRepository.findByUsername(username)` (from `@AuthenticationPrincipal`); `404` if not found (no fallback).
2. `RecommendationClient.getRecommendations(userId, page, size)` → `GET http://recommendation:8000/feed?user_id=&page=&size=` via `RestClient` (`RestClientConfig.java:13` `baseUrl=${recommendation.base-url}` / `RECOMMENDATION_URL`, `SimpleClientHttpRequestFactory` with 1500 ms connect/read timeout, 500 ms in tests).
3. Extract IDs (skip `NumberFormatException`, `log.warn`), `total` from response.
4. Hydrate `findAllByIdsFiltered(rankedIds)` (`WHERE id IN :ids AND deletedAt IS NULL`), build `Map<id,Post>`, reorder to `rankedIds` order, filter `null`/`deletedAt`, map to `PostResponse`, `new PageImpl<>(content, pageable, total)`.
5. On `rankedIds.isEmpty()` or any `Exception` (timeout, `RestClientException`, `null` body) → `log.warn` and fallback to `getChronological(pageable)` (graceful degradation); transparent to client — identical `Page<PostResponse>` shape.
6. Logs `REQUEST_FEED` with `metadata {feed_type: recommended}` via `EventLogService` (async, best-effort).

`docker-compose.yaml` exposes backend `8080`, recommendation `8000`, Postgres `5432`, frontend `3000` (see [7-Frontend.md](./7-Frontend.md)), and sets `RECOMMENDATION_URL` for backend.
