# Analytics Service

This document describes the Analytics Service — an independent Python (FastAPI) service that aggregates `event_logs` and `users` data into statistical reports for administrators (UC-16).

It covers purpose, project structure, quickstart, configuration, shared query conventions, API reference, testing/CI, and implementation status. It reflects the **current state of the implementation**.

---

## Overview

The Analytics Service does not manage users or store application data. It reads the shared PostgreSQL database and returns aggregated metrics over a requested time range. Unlike the Recommendation System, which sits on the critical path of feed requests, analytics runs offline and never affects user-facing latency.

Key properties:

- Offline — pure read aggregation over `event_logs` / `users` (no writes)
- Stateless — can be horizontally scaled
- Shared database — reads only; heavy interval queries are bounded by `MAX_BUCKETS`
- No auth (internal network, like the recommendation service)

Dashboard coverage (UC-16):

| Dashboard item | Endpoint |
|---|---|
| Active users | `GET /users/active`, `GET /usage/activity`, active in `GET /users/engagement` |
| Peak activity hours | `GET /usage/peak-hours` |
| Engagement charts | `GET /users/engagement`, `GET /events/breakdown` |
| Average feed viewing time | `GET /engagement/viewing-time` |
| Most active users | `GET /users/most-active` |

## Project structure

```
intelligence/analytics/
  main.py              # App setup only: lifespan + include_router × 6
  api/                 # One router module per domain (routes + response models)
    activity.py        # /users/active, /usage/activity
    breakdown.py       # /events/breakdown
    engagement.py      # /users/engagement
    peak_hours.py      # /usage/peak-hours
    viewing_time.py    # /engagement/viewing-time
    rankings.py        # /users/most-active
    _common.py         # or_422(): ValueError -> HTTP 422
  db/
    pool.py            # Shared AsyncConnectionPool (min 2, max 10)
    queries/           # One module per domain + _common.py
  tests/               # stdlib unittest + fakes.py (fake async pool)
```

Shared query helpers live in `db/queries/_common.py`: `parse_interval`, `build_bucket_starts`, `gap_fill`, `MAX_BUCKETS = 1000`, `validate_range`, and `resolve_buckets` (range + interval + bucket-guard in one call). Pool connections are imported lazily inside query functions so pure helpers stay importable without database configuration.


## Shared conventions

- **Time ranges** are half-open `[start_time, end_time)`; `start_time >= end_time` is rejected with `422`.
- **Intervals** use duration strings `15m`, `1h`, `1d`, `1w` (strict lowercase; `1M` is rejected to avoid month/minute ambiguity). Raw input is never interpolated into SQL — it maps through a whitelist to a Postgres interval literal.
- **Buckets align to `start_time`** (`date_bin(..., origin=start_time)`), and empty buckets are **zero-filled** (except `GET /users/active`, which returns sparse hourly groups).
- **Validation errors** (`ValueError`) map to HTTP `422` via `or_422` (`api/_common.py`).
- **Bucket guard**: at most `MAX_BUCKETS = 1000` buckets per request, else `422`.
- **Hours and timezones**: hour-of-day aggregation is pinned to UTC (`AT TIME ZONE 'UTC'`); all other timestamps pass through as given (ISO 8601).
- **`limit`** on leaderboards defaults to 10, valid range 1–100 (`422` outside).

## API Reference

### `GET /users/active`

Hourly distinct active users in range (sparse — hours without events are omitted, not zero-filled).

- **Params:** `start_time`, `end_time`
- **Response `200`:** `[{"period_start": "...", "active_users": 12}, ...]`

### `GET /usage/activity`

Distinct active users per interval bucket, gap-filled with zeros.

- **Params:** `start_time`, `end_time`, `interval` (required, e.g. `1h`)
- **Response `200`:**
```json
{
  "start_time": "...", "end_time": "...", "interval": "1h",
  "buckets": [{"period_start": "...", "active_users": 12}, ...]
}
```

### `GET /events/breakdown`

Event counts per type, with optional per-interval series (stacked-bar data).

- **Params:** `start_time`, `end_time`, `interval` (optional)
- All 13 known types (`VIEW_POST`, `LIKE_POST`, `DISLIKE_POST`, `CREATE_COMMENT`, `REPOST_POST`, `FOLLOW_USER`, `UNFOLLOW_USER`, `VIEW_PROFILE`, `CREATE_POST`, `REQUEST_FEED`, `LOGIN`, `REGISTER`, `QUOTE_POST`) are always present, zero-filled. The list mirrors the `event_type` enum (`V1` plus `REGISTER`/`QUOTE_POST` from `V7`) — keep `KNOWN_EVENT_TYPES` (`db/queries/event_breakdown.py`) in sync when the backend adds types.
- **Response `200`:**
```json
{
  "start_time": "...", "end_time": "...", "interval": "1h",
  "totals": [{"event_type": "LOGIN", "count": 1240}, ...],
  "buckets": [{"period_start": "...", "counts": {"LOGIN": 41, ...}}, ...]
}
```
(`buckets` is `null` when `interval` is omitted.)

### `GET /users/engagement`

Total, active, new, and returning users, with optional per-interval series.

- **Params:** `start_time`, `end_time`, `interval` (optional)
- Definitions: **new** = `users.created_at` in range (event logging is best-effort, so `REGISTER` events would undercount signups); **returning** = active in range and created before the range (per bucket: before that bucket's start); **total** = `status='ACTIVE'` snapshot as of `end_time` (per bucket: cumulative as of bucket end). Active users are distinct event actors regardless of status.
- New signups count even if inactive in their bucket, so per bucket `new + returning` does not necessarily equal `active`.
- **Response `200`:**
```json
{
  "start_time": "...", "end_time": "...", "interval": "1d",
  "totals": {"total_users": 100, "active_users": 60, "new_users": 10, "returning_users": 50},
  "buckets": [{"period_start": "...", "total_users": 95, "active_users": 30, "new_users": 5, "returning_users": 25}, ...]
}
```

### `GET /usage/peak-hours`

Event counts and distinct active users per hour-of-day (UTC) over the range.

- **Params:** `start_time`, `end_time`
- All 24 hours returned zero-filled; `peak_hour` is the hour with most events (ties toward the earlier hour).
- **Response `200`:**
```json
{
  "start_time": "...", "end_time": "...", "timezone": "UTC",
  "peak_hour": {"hour": 18, "event_count": 900, "active_users": 200},
  "buckets": [{"hour": 0, "event_count": 12, "active_users": 5}, ...]
}
```

### `GET /engagement/viewing-time`

Average post viewing time from dwell rows (`VIEW_POST` with `metadata.duration_ms`, written by `POST /api/posts/{id}/dwell` — see [5-Backend.md](./5-Backend.md)), with optional trend and source filter.

- **Params:** `start_time`, `end_time`, `interval` (optional), `source` (optional: `FEED` or `DETAIL`, else `422`)
- Values guarded by a numeric regex and clamped to the backend's valid range (`1..1800000` ms); rows without a `source` key report under `"UNKNOWN"` instead of being dropped. Bucket overall averages are weighted from per-source sums, never averaged from averages. Empty scopes yield `average_duration_ms: null, samples: 0`.
- **Response `200`:**
```json
{
  "start_time": "...", "end_time": "...", "interval": "1h",
  "overall": {"average_duration_ms": 4500.0, "samples": 100},
  "by_source": {"FEED": {"average_duration_ms": 5000.0, "samples": 60}, ...},
  "buckets": [{"period_start": "...", "average_duration_ms": 4600.0, "samples": 20, "by_source": {...}}, ...]
}
```

### `GET /users/most-active`

Leaderboard of users by event count in range.

- **Params:** `start_time`, `end_time`, `limit` (default 10, 1–100)
- Every logged event counts (impression and dwell rows alike); the `users` join drops `NULL` actors from deleted accounts.
- **Response `200`:**
```json
{
  "start_time": "...", "end_time": "...", "limit": 10,
  "users": [{"user_id": 7, "username": "feri", "display_name": "Feri", "event_count": 900}, ...]
}
```

No auth on any endpoint (relies on internal network, like the recommendation service).

## Testing & CI

Stdlib `unittest` (no test runner dependency), pool fully faked (`tests/fakes.py` serves single or queued result sets per fetch):

```bash
cd intelligence/analytics
PYTHONPATH=.. uv run python -m unittest discover -s tests
```

`.github/workflows/analytics.yml` runs the same command on every push/PR touching `intelligence/analytics/**` (plus `workflow_dispatch`); no database service is needed.
